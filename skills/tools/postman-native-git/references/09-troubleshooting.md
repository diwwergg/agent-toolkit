# Troubleshooting

## Postman does not recognize a collection

Check:

1. collection directory is under a discovered `postman/collections` path or registered in `.postman/resources.yaml`;
2. collection metadata/resource directory exists in the same pattern as working collections;
3. request files use `.request.yaml`;
4. filenames do not collide case-insensitively;
5. run `postman collection lint <collection-path>`.

## Python validator passes but CLI lint fails

The CLI wins. The bundled validator is structural and intentionally incomplete.

Fix the exact CLI diagnostic, preferably by comparing with a request generated by the same installed Postman version.

## Query parameter format is rejected

A 2026 Native Git issue showed Postman-generated `queryParams` could still trip a format diagnostic in some versions. Do not guess a new universal syntax.

Use this recovery order:

1. inspect a currently lint-clean sibling request with query params;
2. recreate/save one request in the installed Postman app if available and compare the generated YAML;
3. encode a simple query directly in the URL when semantically safe;
4. rerun CLI lint;
5. only then consult current online docs/issues if needed.

## Large noisy diff after opening Postman

Do not automatically commit it. Determine whether Postman reformatted or regenerated IDs/order values. Keep task changes isolated where possible.

## Duplicate collection JSON and v3 YAML

Identify which one the project actually runs/syncs. If both are generated outputs, document the generation direction. Avoid editing both by hand.

## CLI unavailable on an offline server

Use bundled scripts for structure and secret checks. Make the Git change, then run authoritative CLI lint in CI or on a developer workstation that already has Postman CLI installed.
